# Linux UI baseline

The Linux UI is based on Server Man commit `c1a9f32f5898146ae7ac339043b910b8e2a2c438` (Svelte 5 / TypeScript). Reuse upstream components wherever possible. Preserve Maestro session setup, module discovery, per-operation capabilities and the existing router UI. Do not import the ASUS theme or modify `web/`.

Shared Nginx, certificates and Ban Shield should follow the corresponding router page information layout but use the Server Man panel, table, dialog and theme primitives. Existing shared REST routes require bearer authentication, while Linux browser sessions use separate origin-checked session authorization. The Linux-only `/api/shared/` inventory routes use the existing origin-checked session authentication middleware. Nginx, certificates and Ban Shield are presented with Server Man panels and tables and the original router information layout. They use explicitly registered session routes with native configuration and origin checks; privileged operations remain subject to the host helper policy. Certificate hook environment values are never sent to the Linux UI. The router UI remains unchanged; shared APIs reuse the existing renderer and enforce platform-specific limitations.

Validate with `npm ci && npm run check && npm run build` in `linux-web`, followed by Linux integration tests against the live Rust API. Compare the original UI's tool arguments/results with Maestro contracts and test both helper-present and helper-absent modes.

## Shared modules on Linux

The native session UI exposes explicit shared routes for Nginx, certificate definitions and ACME operations, Ban Shield observation and optional enforcement, Wake-on-LAN, AdGuard Home configuration/filtering/rewrites, and WireGuard service lifecycle and offline peer editing. Use the private Linux YAML authority; existing bearer routes are unchanged. Nginx must be initialized using `maestro --config <private-yaml> init-nginx`; use unprivileged listeners and operator-managed port forwarding. DNS challenge credentials/hooks stay on the server. Enable AdGuard through Network rather than router dnsmasq files. WireGuard expects the root-owned `/etc/wireguard/wg0.conf` and the exact `wg-quick@wg0.service` unit authorized by the optional root-owned helper policy. The separate wireguard_peers grant permits public peer configuration editing while the interface is stopped. It does not expose private keys or arbitrary privileged command execution. Ban Shield enforcement uses the dedicated root-authorized nftables table. Nginx site settings have dedicated controls and advanced JSON; Ban Shield rule policy uses JSON.

### Nginx configuration

Linux now exposes the full shared global and site settings through the session API and Svelte editors. Advanced nested routes can be edited as JSON alongside simple path controls. Listener and access usage and effective-access previews use the common renderer. Router-specific WAN rules are rejected on Linux; configure external ingress instead.
